# 知识对象、属性与关系 V0.1

## 三个相互独立的维度

**类型（type）**回答“是什么”：实体、材料、工艺、工序、配置、性能、证据、成本、活动、交付、商业包等。

**关系（relation）**回答“和谁如何相连”：包含、使用、采用、先后、支持/反驳、条件限制、依赖工作、实现成果。关系有方向，不能仅靠共现标签推断。

**属性（attribute）**回答“有什么可量化或可描述的特征”：材料厚度、产量、涂刷遍数、面积、单价、目标膜厚、条件范围、来源状态。单位、量纲、测量/计价口径应可表达。

## 角色与本体边界

门锁的主类型是 physical_object，不因装配到门里就被重定义成 component；它可通过 has_part 关系被门包含，也可在销售场景中独立作为商品。结构与构造 construction 可以描述抽象构成方式；物体 physical_object 描述可识别的实体类型。

涂料中的基础材料、复合材料、构造层次可根据可复用性继续分解；不得用一个无条件的 has_part 取代成分包含、结构层次和步骤先后等不同关系。

**案例**不是“永远按这套工程做”；**配置**不是“标准必须这样做”；**问题**不是默认节点；纯参数值通常不单独成卡。

## 节点最小结构

所有知识 Markdown 采用 YAML front matter。通用必填：schema_version、id、type、title、status、summary、scope、relations。正式内容逐步增加 authors、reviewed_at、references、claims、parameters 与版本变更说明。

- id 不随重命名更改。
- scope 表示领域、地域、条件或待补充状态，不允许把未说明的适用条件伪装成通用结论。
- status 建议：draft / unverified / reviewed / deprecated。
- relations 中 kind 必须在关系注册表中定义，target 指向存在的节点 ID。
- 所有事实主张的证据支持关系独立于“同名标签”。

## 何时增新节点

若一个概念可被多个对象复用、可被独立引用、拥有自身证据、版本或专业争议，则建立节点；否则优先留作节点的参数/属性。新类型需通过 ADR 说明为什么现有类型无法表达。

## 当前类型注册表

权威类型以 ontology/types.yaml 为准。这里保留可扩充类型，不将“12+4”理解为永久上限。工序、配置、工作活动、交付成果和商业包是对前期讨论的补充，不应粗暴塞进“工艺”和“成本”备注字段。

## 实施提示

知识图谱与图数据库不同：本阶段文件是权威数据源，索引图只是派生结构。将来若采用 Wikibase、Argdown、Nanopublications、PROV-O 等思想，应映射已有对象/证据，而不是重录第二套事实。Obsidian 的双向链接可以作为编辑和探索视图，但机器关系仍以稳定 ID 为准。
